# 도소매 콘텐츠 제작 — 모델·서비스 연동 초안

작성: 2026-09-10 · 상태: **팀 협의용 draft-0.1 / 미구현**

구현 현황: 이 문서의 draft 계약과 구분되는 [mock-0.1 상세페이지 API](detail_page_mock.md)가 추가되었다.
공통 상품 입력·섹션/블록 JSON 구조만 실행 가능하며 실제 생성·수정·저장은 아직 별도 작업이다.

UI 자료 검토 반영: [Page Smith 화면별 모델 대응표](ui_model_mapping.md).
이미지 기반 자동 완성, 블로그, 상품등록 보조, 채팅 블록 수정과 작업 상태 요구를 추가 정리했다.
draft-0.1 예시는 섹션 단위 최소 계약이다. 블록 단위 편집·장수·언어 등 UI 확장은 대응표의
협의 사항을 확정한 뒤 다음 스키마 버전에 반영한다.

## 이번에 합의할 방향

상품 정보를 한 번 정리한 뒤 상세페이지·광고·블로그에 재사용한다. 모델은 콘텐츠와 섹션
구조를 JSON으로 반환하고, 서비스는 HTML/CSS 템플릿으로 표시·편집한다. 모델이 임의의
HTML이나 JavaScript를 만들어 실행하도록 하지 않는다. 최종 HTML/이미지 내보내기는 서비스 담당이다.

**현재 `POST /v1/generate`와 별도 설계다. 아래 예시는 현재 CLI/API에 넣으면 안 된다.**
현재의 `detail_visual`은 대표 이미지 한 장이다. 새 `detail_page`는 섹션 여러 개의 콘텐츠 문서다.
기존 실험·생성 API는 유지하고 팀 합의 후 새 스키마와 어댑터를 구현한다.

## 담당 구분

| 기능 | 모델 파트 | 서비스·프론트 파트 |
|---|---|---|
| 상품 입력 | 공통 상품 정보 검증, 누락 정보 반환 | 입력 폼, 업로드, 사용자·상품 소유권 확인 |
| 스마트스토어 연결 | 전달받은 상품 정보의 콘텐츠 활용 | 인증, 상품 조회·등록, 필드 변환, 등록 전 확인 |
| 상세페이지 | 섹션 구성·문구·이미지 생성 및 부분 재생성 | 템플릿 렌더링, 순서·스타일 편집, 내보내기 |
| 블로그 | 상품 사실 기반 제목·본문·이미지 배치 제안 | 편집 화면, 저장, 게시 연동 |
| 실행 관리 | 단계별 진행·사용량·오류 전달 | 작업 큐, 상태 표시, 권한, 재시도·중복 요청 관리 |

스마트스토어를 선택했다는 것만으로 연결·조회·등록이 실행되지는 않는다. 게시·등록은 별도
사용자 확인을 거친 서비스 작업이다. 플랫폼 연동 규격·권한은 서비스 파트에서 별도 확인한다.
비영리 운영과 API/GPU 비용은 별개이므로 호출 한도·사용량 기록을 유지한다.

## 1. 공통 입력

예시: [상품 정보와 상세페이지 생성 요청](contracts/draft-0.1/detail_page.request.json)

| 필드 | 용도·규칙 |
|---|---|
| `schema_version` | 계약 버전. 이번 예시는 `draft-0.1` |
| `request_id` | 호출 식별자. 서비스가 발급하고 사용자 소유 작업에 연결 |
| `product.product_id`, `revision` | 상품 식별자와 정보 버전. 생성 중 원본 변경을 구분 |
| `product.name`, `category_path` | 상품명과 범용 카테고리 경로. 식료품 enum 고정 해제 |
| `product.facts[]` | 규격·재질·특징·주의사항 등 확인된 정보. 사실마다 `fact_id`와 출처 보관 |
| `product.images[]` | 업로드 자산 ID, 역할, 원본 크기, 선택 박스. 로컬 경로나 임의 URL 대신 ID 사용 |
| `product.missing_fields[]` | 아직 없는 정보. 모델이 추측으로 채우지 않음 |
| `content_request` | 결과 종류, 타깃, 톤, 언어, 섹션 계획, 이미지 처리 방식 |
| `execution` | 모델 호출 예산, 재시도 한도. 실제 모델 선택은 서버 허용 목록으로 관리 |

`facts`는 판매자 입력 또는 연결된 상품 정보 등에서 온 사실이다. 출처 표시는 외부 진실 검증을
뜻하지 않는다. 가격·인증·효능·원산지·배송 등 확인되지 않은 정보를 생성하지 않는다. 상품명과
사진만 있을 때는 알 수 없는 규격을 질문하거나 해당 섹션을 생략한다. 카테고리별 필요한 항목은
추가 템플릿으로 확장하며, 모든 업종에 같은 규격 목록을 강제하지 않는다.

사진 박스는 EXIF 방향을 적용한 원본 기준 `[xmin, ymin, xmax, ymax]` 픽셀 좌표다.
`0 <= xmin < xmax <= width`, `0 <= ymin < ymax <= height`를 검증한다. 서비스는 자산 ID를
권한 확인 후 내부 파일로 해석하며, 모델에는 필요한 상품 자료만 제공한다. API 키·판매자 토큰은
모델 프롬프트나 JSON에 넣지 않는다. 상품 설명·수정 지시도 보안 규칙을 덮어쓰는 명령으로 취급하지 않는다.

이미지 처리: 원본 보존형 `composite`를 기본으로 하고 박스가 있으면 SAM2, 없으면 BiRefNet을
선택한다. `direct_edit`은 명시 요청만 허용하고 포장 변형 검수가 필요하다. 사진이 없는 생성 이미지는
실물 보존 결과로 표시하지 않는다. 이미지 판단 실패 시 사용자가 박스를 지정하거나 사진을 바꾸도록 안내한다.

## 2. 상세페이지 출력

예시: [섹션별 결과](contracts/draft-0.1/detail_page.response.json)

**예시는 가상 머그 상품의 수작업 계약 샘플이다. 모델 생성 결과나 실험 성능 자료가 아니며,
자산 ID도 설명용이다. 실제 이미지 파일·URL은 제공하지 않는다.**

- `document_id`, `revision`: 저장 문서와 버전. 모델이 아니라 서비스가 관리한다.
- `sections[]`: 배열 순서가 화면 순서. 고정된 `section_id`로 선택 수정한다.
- `type`: 예시의 `hero`, `features`, `specifications` 등 서비스가 지원하는 블록 종류.
- `content`: 제목·본문·정보 항목. `fact_refs`는 근거 추적용이며 허위 주장 검증을 대신하지 않는다.
- `layout`: `image_text`, `feature_list`, `spec_table` 같은 의미 중심 레이아웃 힌트.
  정확한 좌표·폰트·반응형 디자인은 프론트 템플릿이 결정한다.
- `image`: 자산 ID와 대체 텍스트. `layers`는 배경·누끼·합성본을 분리해 재사용하기 위한 정보다.
- `review`: 누락 정보와 사람 확인 여부. `needs_review` 결과를 자동 게시하지 않는다.
- `execution`: 실제 경로·제공자·토큰·비용·단계별 시간은 실행기가 측정한다. 모델이 수치를 작성하지 않는다.
  샘플의 `null`은 미측정이며 무료라는 뜻이 아니다.

사용 장면·관리법 등은 근거가 있을 때 추가한다. 임의의 후기·인증·할인·효능으로 빈 섹션을 채우지 않는다.
상품 정보표는 가능하면 원본 사실에서 직접 구성한다. 가격과 배송 정보는 서비스의 최신 상품 정보가 우선한다.

## 3. 선택한 부분만 재생성

예시: [수정 요청](contracts/draft-0.1/section_revision.request.json) ·
[수정 응답](contracts/draft-0.1/section_revision.response.json)

1. 서비스가 문서 ID·기준 버전·섹션 ID·수정 대상(`text` 또는 `image`)·지시를 전달한다.
2. 모델 실행기가 해당 버전의 상품 사실과 대상 섹션을 불러온다. 권한은 서비스에서 검증한다.
3. 문구만 수정하면 이미지 모델·누끼 모델은 호출하지 않는다. 배경만 수정하면 기존 문구·누끼를 재사용한다.
4. 변경된 콘텐츠만 반환한다. 서비스가 기준 버전을 확인하고 새 버전으로 저장한다.
5. 다른 섹션과 선택하지 않은 필드는 그대로 유지한다. 기준 버전이 달라졌으면 충돌로 처리하고 덮어쓰지 않는다.

범위 안에서 사실을 유지할 수 없는 요청은 거절하거나 추가 정보를 요청한다. 실패 시 이전 문서는 보존한다.
동일 요청 ID·동일 내용의 재요청은 저장된 처리 상태/결과를 반환하도록 설계한다. 다만 외부 모델 호출 도중
연결이 끊긴 경우 과금 여부가 불명확할 수 있으므로 무조건 다시 호출하지 않고 상태를 확인한다.

## 4. 블로그와의 관계

같은 `product`를 재사용하되 블로그 결과는 제목·도입·본문 블록·이미지 참조·마무리로 별도 정의한다.
상세페이지 문구를 그대로 이어 붙이는 방식은 피한다. 실제 사용 경험이나 고객 후기를 만들어내지 않는다.
UI의 블로그는 등록되지 않은 상품/주제로도 시작할 수 있으므로 기존 상품 ID를 필수로 강제하지 않는다.
**이번 JSON 예시는 상세페이지 우선이며 블로그 요청·응답 계약은 다음 협의 대상이다.**

## 현재 코드와의 차이

| 현재 | 제안 |
|---|---|
| `food_retail` 및 식료품 카테고리 3종 | 범용 카테고리 + 품목별 속성 |
| `text` 설명 문자열 중심 | 출처와 ID를 가진 상품 사실 + 제작 지시 분리 |
| `image_path` 한 장 | 권한 확인 가능한 다중 자산 참조, 주상품 사진 선택 |
| `detail_visual` 한 장 | 안정적 ID를 가진 다중 섹션 `detail_page` |
| 작업 단위 전체 생성 | 섹션·텍스트/이미지 단위 버전 수정 |

기존 편집 화면은 참고용으로 유지한다. 이번 작업에서는 프론트나 실제 생성 API를 확장하지 않는다.

## 팀 확인 사항과 다음 구현 순서

먼저 ① 공통 상품 필드·자산 ID 전달 방식 ② 지원 섹션/레이아웃 종류 ③ 버전 저장·작업 상태의
서비스 담당 ④ 스마트스토어 연동 범위(조회/등록) 를 합의한다.

합의 후 모델 파트는 **검증 스키마·mock 연결 → 이미지 기반 상품 정보 추출 → 섹션 생성·수정 →
블로그 → 등록 보조·다품목 평가** 순서로 구현한다. 자동 완성과 등록 보조는 추출 파이프라인을 공유한다.
유료 실험 전에 mock으로 연결 검증한다. 구체적인 UI 대응·미확정 사항은 위 대응표를 기준으로 한다.

검증 기준: 필수·누락 정보 처리, 허위 사실 방지, 섹션 ID 유지, 참조 자산 유효성,
선택하지 않은 콘텐츠 보존, 실패 시 원본 보존, 재시도 중복/버전 충돌, 모델별 실제 호출량 기록.

계약 예시의 기본 정합성 검사:
`PYTHONPATH=src .venv/bin/pytest -q tests/unit/test_contract_examples.py`
이 검사는 JSON 문법·예시 간 참조·문구 수정 범위만 확인하며, API 구현이나 콘텐츠 품질 검증은 아니다.
