## 안전 경계와 제한

- 모델은 본문 전체 대신 지원 작업 목록과 `ready`/`needs_clarification`만 반환한다.
- 버전·hash·request_id는 모델이 아니라 호출 코드가 입력 문서에서 지정한다.
- 명시적 블록/섹션 선택이 있으면 범위 밖 작업을 코드에서 거부한다.
  선택이 없는 요청의 대상 해석은 모델 판단이므로 미리보기·사용자 승인이 필요하다.
- 결과는 원본을 수정하지 않는 사본이다. 미완료·거부·잘못된 스키마·참조·범위는 실패한다.
- 미확인 사실은 질문으로 돌리도록 지시했다. 이는 프롬프트 정책이지 완전한 사실성
  보장이 아니다. 실제 평가와 판매자 승인 절차가 추가로 필요하다.
- 이미지 편집 요청은 `not_started` 작업 의도로만 표시하며 생성/큐 등록하지 않는다.
- 저장/이력/동시 편집 보호와 HTML 렌더러 반영은 아직 연결하지 않았다.
- 무인 유료 HTTP 엔드포인트는 추가하지 않았다. 현재는 재사용 가능한 Python 제공자와

  그 안의 `preview.model_calls=0`은 순수 검증기만의 호출 수다.

## 실행 및 파일

외부 전송 승인을 받은 환경에서 건별 실행한다. 기존 출력 폴더는 덮어쓰지 않는다.

```bash
PYTHONPATH=src python scripts/run_revision_experiment.py \
  --request /path/requests/01_text.json --output /path/new-results/01_text
```

- `request.json`: 실제 전달할 문서와 지시

- `result.json`: 검증된 제안·미리보기·토큰 사용량·지연시간(성공했을 때)
- `failure.json`: 실패 종류·검토 안내(실패했을 때)

## 2026-09-11 · 스키마 보강 (`revision-planner-0.2` 준비)

### 9/10 실험 결과 재해석

6건 중 3건 실패는 "모델이 요청을 이해하지 못한 것"이 아니었다. 실패한 3건은
모두 **기존 블록을 지목해서 바꾸는 작업**이었고, 성공한 3건은 모두 **대상 지목이
필요 없는 작업**(되묻기 2건, 이미지 의도 표시 1건)이었다.

| 케이스 | 기대 작업 | 실제 반환 |
|---|---|---|
| 01 문구 | `replace_text` | `add_block` |
| 02 배치 | `set_layout` + `set_style` | `add_section` |
| 06 구조 | `remove_section` + `move_section` | `add_section` × 4 |

02번이 반환한 값은 `section_id: "tmp_unused"`, `text: "x"` 였다. 구조화 출력이
선택한 작업의 모든 속성을 필수로 만들기 때문에, 잘못된 작업을 고른 모델이
빈칸을 껍데기 값으로 메운 것이다. 이해력 문제가 아니라 출력 구조 문제다.

또한 당시 `execution.json`에 남은 전송 스키마를 확인한 결과, 실험 시점에는
**작업 12종이 모두 열려 있었다.** 종류를 좁히는 코드는 같은 날 밤에 추가됐다.
따라서 **품질 3/6 이라는 수치는 현재 코드의 성능이 아니다.**

### 이번에 바꾼 것

1. **모호한 지시는 작업을 닫는다.** `allowed_operation_types()`가 빈 집합을
   돌려주면 지시에서 변경 종류를 찾지 못한 것인데, 기존 `allowed or None`
   때문에 오히려 12종 전체가 열렸다. 주석의 의도("모호하면 닫는다")와 동작이
   반대였다. 이제 빈 집합이면 `operations.maxItems = 0` 으로 닫고 질문만 받는다.
2. **대상 ID를 문서에 있는 값으로 고정한다.** `ground_operation_ids()`가 각 작업의
   `block_id` / `section_id` / `asset_id` / `fact_refs` 를 실제 ID의 enum으로 바꾼다.
   `tmp_unused` 같은 값은 스키마 단계에서 생성이 불가능해진다. 문구 수정은 텍스트
   블록만, 이미지 편집은 이미지 블록만 고르게 한다. 대상이 하나도 없는 작업은
   스키마에서 제거한다.
3. **껍데기 값을 거부한다.** `reject_placeholder_values()`가 신규 ID의
   `tmp_` / `dummy_` 접두어와 내용 없는 문구를 미리보기 전에 끊는다.
4. **검증 실패 시 1회 재시도.** 사유를 지시문에 붙여 다시 묻는다. 토큰 초과와
   모델 거부는 결과가 같으므로 재시도하지 않는다. `PlanningResult`에
   `model_calls`(실제 호출 수)와 `retry_count`를 기록한다.

H2는 "제목을 짧게"를 다른 10자 문구로 바꾸고 보정 재시도에서는 원문 10자를
그대로 반환해 실패했다. 일반적인 "짧아지지 않음" 안내만으로는 모델이 제약을
정확하게 복구하지 못했다.

보정 안내에 대상 블록 ID, 기존 글자 수, 허용되는 최대 글자 수, 제안 글자 수를
직접 제공하고 버전을 `0.4`로 올렸다. 기존이 10자면 "9자 이하로 작성"이라고
알려준다. 길이 검사를 단순 동일값 검사보다 먼저 적용해 원문을 그대로 돌려준
경우에도 구체적인 보정 조건을 전달한다.

| 결함 사례 | `0.4` 결과 | 호출 수 | 비고 |

| A4 세 번째 특징 문구 축약 | 통과 | 2 | 원문보다 짧은 문구로 보정 |
| F2 제목 블록 하나 추가 | 통과 | 1 | 요청을 CTA 섹션의 첫 블록으로 명확히 함 |
| H2 문구·배치·구조 복합 수정 | 통과 | 2 | 제목 10자→6자, 배치 변경, 섹션 삭제 |

최초 F2 지시인 "CTA 섹션 위에 제목 블록"은 현재 문서 구조에서 섹션 밖 블록으로
해석될 수 있다. 모델은 임의로 구조를 정하지 않고 확인 질문을 반환했다. 이는 안전한
동작이므로 모델 실패로 세지 않고, 평가 문장을 "CTA 섹션의 첫 블록"으로 명확히
고쳐 다시 측정했다.

이번 재검증의 총 계산 비용은 `0.3` 실패 응답 두 번을 포함해 **$0.04024**였다.
실행기가 검증 실패 응답의 비용을 누적액에서 빠뜨리는 결함도 발견했다. 앞으로는
숫자가 붙은 원시 응답 파일의 사용량까지 합산하고, 실행 출력의 "성공"은 품질
통과와 혼동하지 않도록 "유효 응답"으로 표시한다.

이어 문구·배치·구조·미확인 효능·대화 이력·복합 문구 대조군 6건을 실행했고,
모두 첫 호출에서 통과했다. 결함 3건과 합친 `0.4` 표적 평가의 최종 결과는
**9/9 통과**, 실제 모델 호출 **11회**다. 잘못된 `add_*` 탈출, 무변경 작업,

표적 평가 9건의 전체 사용량은 입력 46,619토큰(캐시 15,360), 출력 1,554토큰이다.
캐시 단가를 반영한 표준 계산 비용은 **$0.03159**이며 실제 청구 내역은 아니다.
디버깅 중 실행한 `0.3`과 모호했던 원래 F2 요청까지 포함한 보수적 계산 총액은
