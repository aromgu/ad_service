# Page Smith UI → 모델 기능 대응표

기준: 2026-09-10 제공된 `UI_데모.zip` 안의 `Page Smith Wireframes.dc.html` 및
`design_handoff_page_smith/README.md`. HTML의 프레임 ID로 아래 항목을 추적한다.
**설계 반영 문서이며, 기능 구현·모델 성능 검증 완료를 의미하지 않는다.**

후속 구현: [상세페이지 JSON mock](detail_page_mock.md)에서 공통 상품 입력과 안정적 섹션/블록 ID를
검증할 수 있다. [자연어 부분 수정·HTML 미리보기·승인 버전 저장](detail_page_revision.md)과
[승인형 이미지 편집 작업](image_edit_jobs.md)과 검수 결과의 새 문서 자산 확정까지 구현되었다.
[생성 작업 상태·이벤트·취소·재시도](generation_jobs.md)도 기존 생성 파이프라인에 연결되었다.
블로그·등록은 아직 설계 또는 후속 구현 항목이다.

UI의 화면 흐름은 참고하되, 회의에서 정한 도소매 범용·비영리 운영과 모델 파트 역할이 우선한다.
번들의 프론트 재구현 지시나 프레임워크 권장은 이번 모델 작업에 적용하지 않는다.

## 1. 화면별 필요한 모델 기능

| 화면 | 실제 자료에서 확인한 동작 | 모델 입력 → 출력 | 경계 |
|---|---|---|---|
| 2a / 2a-2 상세페이지 입력 | 상품명, 타깃, 언어(자동), 감성적/정보 중심, 길이, 특징, 사진 최대 5장 | 공통 상품 정보 + 생성 옵션 → 섹션별 상세페이지 | 폼·업로드는 서비스 |
| 2a 자동 완성 | 기존 상세페이지 이미지로 상품명·타깃·특징 채움 | 참조 이미지 ID → 추출 후보·근거 위치·누락 정보 | 후보를 확인받은 뒤 상품 사실로 반영 |
| 2b 생성 중 | 정보 분석 → 카피 작성 → 레이아웃 구성 → 이미지 배치, 취소 | 실제 처리 단계 이벤트·실패 이유 | 큐·화면 전환은 서비스; 퍼센트/시간을 임의 생성하지 않음 |
| 2c / 2d 상세 에디터 | 채팅 수정, 선택 블록, 이미지 교체/크롭, 섹션 숨김/순서 | 문서 버전 + 선택 범위 + 수정 지시 → 제한된 변경안 | 직접 글자 편집·스타일·크롭·순서 변경은 모델 불필요 |
| 3a 블로그 입력 | 주제/상품명, 스타일, 사진, 추가 요청 | 등록 상품 없이도 주제·근거·사진 → 글 초안 | 등록 상품 ID를 필수로 강제하지 않음 |
| 3b / 3c 블로그 생성·편집 | 주제·키워드, 목차, 본문, 사진·태그, 본문 복사, 채팅 | 제목·본문 블록·사진 참조·태그·수정안 | 게시·복사·공유는 서비스; 검색 순위 보장 없음 |
| 4a / 4b 상품 분석 | 상세 이미지 OCR, 브랜드·분류, 상품명·태그, 옵션·인증 정보 | 참조 이미지와 판매자 정보 → 등록 필드 후보·근거·확인 필요 항목 | 배송 설정·연락처·주소는 모델에 넘길 필요 없음 |
| 4c 검토·등록 | 후보 수정, 가격·재고, 분류 추천, 옵션, HTML 변환, 등록 | 근거 있는 설명·태그·분류 후보 | 실제 분류 ID 매핑·재고·가격·인증 확인·등록은 서비스/판매자 |
| 5a / 5b 내 작업 | 유형·상태별 목록, 실패 재시도, 삭제 | 모델은 작업 유형·상태·오류·결과 참조 제공 | 소유권·목록·삭제·버전 저장은 서비스 |

## 2. 기존 초안에 보완할 필드

| 구분 | 제안 필드 | 의미 |
|---|---|---|
| 자료 종류 | `reference_documents[]` | 기존 상세페이지 이미지. 상품 사진 `product.images[]`와 구분 |
| 추출 후보 | `candidates[].field/value/evidence/requires_confirmation` | OCR 사실 후보와 타깃 같은 마케팅 제안을 구분 |
| 언어 | 요청 `language: auto`, 응답 `resolved_language` | 미해결 시 언어를 질문. 한국어 기본값 적용 여부는 서비스 정책으로 명시 |
| 길이 | `page_length`, `section_limit` | 예산·섹션 수 상한 제안. 이미지 10장 생성과 동일시하지 않음 |
| 섹션 표시 | `sections[].visible` | 숨김 상태도 저장. 순서는 배열 순서를 기준으로 사용 |
| 블록 선택 | `block_id`, `selected_block_id` | 텍스트/이미지의 안정적인 선택 단위. 재생성 때 ID 유지 |
| 채팅 | `message_id`, `base_revision`, `instruction`, 선택 범위 | 의미가 모호하면 `needs_input`과 확인 질문을 반환 |
| 작업 | `job_id`, `status`, `stage`, `sequence`, `error` | 실행기가 갱신하는 실제 상태 |

`block_id`는 기존 `content` 구조에 무작정 병행 추가하지 않는다. 다음 스키마 작업에서
섹션 안 `blocks[]` 형태로 정규화하고 문구/이미지 참조를 한 곳에서 관리한다.
현재 draft-0.1 JSON은 **섹션 단위 수정 예시**이며 블록 선택까지 지원하는 계약은 아니다.

자료에 `order`와 배열 순서가 함께 있지만, 초안은 배열을 순서의 단일 기준으로 제안한다.
프론트에서 `order`가 필요하면 서비스 어댑터가 계산한다. 숨김·스타일 상태는 모델 응답으로 초기화하지 않는다.

## 3. 자동 완성은 ‘확정’이 아니라 ‘추출 → 확인’

새 계약 예시: [이미지 분석 요청](contracts/draft-0.1/product_analysis.request.json) ·
[분석 후보 응답](contracts/draft-0.1/product_analysis.response.json)

1. 상품 사진과 기존 상세페이지 이미지를 구분해서 받는다.
2. OCR/이미지 이해로 상품명·규격·특징 등의 후보를 추출한다. 사용 모델은 아직 미선정이다.
3. 읽은 문자열과 이미지 내 근거 박스를 함께 돌려준다. 안 보이는 정보는 `unknown`으로 둔다.
4. 타깃·태그·분류는 관찰 사실과 다른 **추천 항목**으로 표시한다.
5. 판매자가 확인·수정한 내용을 버전이 있는 공통 `product.facts`로 저장한 뒤 생성에 쓴다.

판매자 입력은 이미지 추출보다 우선하지만, 충돌은 숨기지 않고 확인 항목으로 반환한다.
이미지 안의 지시문·URL을 실행하지 않는다. 외부 상세페이지에서 읽힌 효능·인증·후기 문구도
독립적으로 확인된 사실이 아니라 원문에서 추출된 주장으로 취급한다.

## 4. 사용자 수정 지시 분기

- “제목을 짧게”: 선택 텍스트 블록만 변경. 사실·이미지·나머지 섹션 보존.
- “배경을 밝게”: 선택 이미지의 배경만 생성. `composite`면 기존 상품 누끼 재사용.
- “글자색을 파랗게”, “2번 섹션 숨겨줘”: 서비스 편집 동작으로 처리. 생성 모델 불필요.
- “이거 좀 바꿔줘”인데 선택 없음: 대상을 되묻고 원본을 유지.
- “후기에 다들 좋다고 써줘”: 실제 후기 근거를 요청. 허구 후기를 만들지 않음.

모델 출력은 허용된 변경 구조로 검증한다. 임의 파일 편집·코드 실행·HTML 실행 도구는 제공하지 않는다.
채팅 UI의 ‘파일 보기’ 등 문구가 실제 파일 시스템 접근 권한을 요구하는 것은 아니다.

## 5. 진행·취소·재시도 계약 방향

아래 계약은 `generation-job-0.1`로 구현되었다. 현재는 기존 광고 생성 파이프라인을 실행하며,
다중 섹션 상세페이지 통합 실행기가 완성되면 같은 이벤트 계약에 해당 단계를 추가한다.

작업 상태는 `queued → running → succeeded | failed | cancelled`를 기본으로 하고,
추가 확인이 필요하면 `needs_input`에서 멈춘다. 문서의 `needs_review`는 작업 실패가 아니라
생성이 끝난 콘텐츠의 검수 상태다. 이벤트는 `sequence`로 오래된 갱신을 구분한다.

상세 단계는 검증·상품 분석·섹션 계획·문구 생성·이미지 처리·결과 검증을 실제 실행에 맞춰 보낸다.
프론트는 이를 UI의 네 단계로 묶어 표시할 수 있다. 정확한 퍼센트/잔여시간이 없으면 `null`로 보내고
단계 기반 표시를 쓴다. 42%, 40초 등의 화면 숫자를 실행 실적으로 기록하지 않는다.

취소 요청을 받으면 후속 호출을 중단한다. 이미 실행 중인 외부 호출은 즉시 취소되지 않을 수 있어
`cancel_requested`와 최종 `cancelled`를 구분하고 발생 비용은 남긴다. 실패 재시도는 기존 성공 자산을
재사용할 수 있는지 확인한 뒤 예산을 점검한다. 취소나 재시도로 이전 완성 문서를 덮어쓰지 않는다.

## 6. 자료에서 그대로 확정하면 안 되는 부분

| 자료 내용 | 확인/보완 방향 |
|---|---|
| 블로그 사진 ‘최대 5장’ 설명, 업로드 라벨은 ‘1~8장’ (3a) | 서로 다름. 블로그 최대 장수는 팀 확인 전 미확정 |
| ‘숏(10장 내외)’ (2a), 에디터 예시는 5섹션 | 장=이미지/섹션/출력 조각 중 무엇인지 합의. 10회 이미지 호출로 해석하지 않음 |
| ‘일반/메뉴판’ (2a) | 메뉴판 선택은 보이지만 전용 출력 구조가 없음. 별도 계약 필요 |
| ‘자동’ 언어, ‘상세 설정’ 접힘 (2a) | 지원 언어·감지 실패 처리·고급 설정 상세는 미정 |
| 블로그/상품등록 ‘준비 중’ 태그와 별도 화면 모두 존재 | 기능 방향은 포함하되 출시 순서는 팀 결정 |
| ‘3초’, ‘3분’, ‘40초’, ‘30초’ 등 | 검증된 지연시간 보장이 아님. 모델 평가 후 안내값 정함 |
| ‘3주 써본 기록’, 임상 수치, 후기 섹션 | 실제 근거가 없으면 생성/인용하지 않음 |
| ‘KC인증 판별’, 대상 아님 선택 예시 | 이미지 미검출을 인증 없음/대상 아님으로 바꾸지 않음. `unknown` 유지 후 별도 확인 |
| 카테고리 ‘AI 95%’ | 보정된 확률 검증 전 퍼센트 신뢰도로 제시하지 않음. 후보 순위·추천 이유 사용 |
| 재고 999, 옵션 재고·가격, 제조사/판매자 코드 | 예시 값을 실제 기본값으로 쓰지 않음. 판매자/연동 정보가 필요 |
| ‘HTML로 바꾸기’ | 서비스 템플릿으로 직렬화하는 것과 OCR로 원본 레이아웃을 복원하는 것은 다름. 지원 범위 협의 |
| 요금제 메뉴 | 비영리 회의 결정에 맞춰 서비스 팀이 조정. 비영리라도 운영비 관리 필요 |

위 내용은 구현 안전장치 제안이며 특정 상품의 인증 의무나 플랫폼 규정에 대한 판단이 아니다.

## 7. 모델 파트 실행 순서 (UI 반영)

1. **입출력 스키마 + mock**: 상세 입력, 다중 이미지 역할, 섹션/블록 ID, 선택 수정, 작업 상태 검증.
2. **상품 정보 추출 실험**: 기존 상세 이미지 → 근거 있는 후보 → 판매자 확인 흐름. 자동 완성·상품등록이 공유.
3. **다중 섹션 생성·수정**: 검증된 사실로 문구 생성, 필요한 이미지만 생성, 보존 범위 평가.
4. **블로그**: 등록 여부와 독립적인 주제 입력, 본문·사진·태그 생성, 허구 체험 방지 평가.
5. **등록 보조**: 분류/속성 후보를 서비스에 전달. 서비스의 카테고리 목록·필수 필드 계약에 맞춰 검증.

OCR 정확도, 중요 상품 사실의 정확성, 누락/충돌 탐지, 원본 상품 보존, 변경 범위 보존,
호출 비용/시간을 평가한다. UI 제작·네이버 등록 실행은 이번 모델 작업의 범위가 아니다.
